# Database Schema

This document records the agreed application database schema for CupQueue. PostgreSQL is the source of truth, and Flyway migrations under `backend/src/main/resources/db/migration` must implement every schema change described here.

## Conventions

- Primary keys use PostgreSQL identity columns.
- Audit timestamps are generated and maintained by PostgreSQL.
- Status, role, and gender values are stored as stable uppercase codes and translated for display by the application.
- Usernames are case-sensitive and unique. For example, `admin` and `Admin` are different usernames.
- Passwords are never stored directly. Only a secure password hash is persisted.
- Country, province, currency, and timezone values use standard codes where applicable.

## `stores`

Stores a physical Coffee & Tea location and its current operating status.

| Column | Data type | Constraints | Description |
| --- | --- | --- | --- |
| `id` | `BIGINT` | Primary key; generated by default as identity | Internal store identifier. |
| `name` | `VARCHAR(100)` | Not null; unique | Store name, such as `Coffee & Tea`. Future branches should use distinguishable names. |
| `status` | `VARCHAR(20)` | Not null; default `PREPARING`; check constraint | Current store status. Allowed values: `PREPARING`, `OPEN`, and `CLOSED`. |
| `location` | `VARCHAR(255)` | Not null | Street address, building, unit, or campus location details. |
| `city` | `VARCHAR(100)` | Not null | City in which the store is located. |
| `province` | `CHAR(2)` | Not null; two-uppercase-letter check constraint | Canadian province or territory code, such as `BC`. |
| `country` | `CHAR(2)` | Not null; default `CA`; two-uppercase-letter check constraint | ISO 3166-1 alpha-2 country code. |
| `postcode` | `VARCHAR(10)` | Not null | Postal code. It is stored as text to preserve letters, spaces, and leading characters. |
| `timezone` | `VARCHAR(50)` | Not null | IANA timezone name, such as `America/Vancouver`. |
| `currency` | `CHAR(3)` | Not null; default `CAD`; three-uppercase-letter check constraint | ISO 4217 currency code. |
| `created_at` | `TIMESTAMPTZ` | Not null; default `CURRENT_TIMESTAMP` | Time at which the store record was created. |
| `updated_at` | `TIMESTAMPTZ` | Not null; default `CURRENT_TIMESTAMP`; database update trigger | Time at which the store record was last updated. |

### Store status values

| Value | Meaning |
| --- | --- |
| `PREPARING` | The store is being prepared and is not yet open for business. |
| `OPEN` | The store is currently open for business. |
| `CLOSED` | The store is currently closed. |

### Store constraints and indexes

| Name | Type | Definition |
| --- | --- | --- |
| `stores_pkey` | Primary key | `id` |
| `stores_name_unique` | Unique constraint | `name` |
| `stores_status_check` | Check constraint | `status IN ('PREPARING', 'OPEN', 'CLOSED')` |
| `stores_province_check` | Check constraint | `province ~ '^[A-Z]{2}$'` |
| `stores_country_check` | Check constraint | `country ~ '^[A-Z]{2}$'` |
| `stores_currency_check` | Check constraint | `currency ~ '^[A-Z]{3}$'` |
| `stores_set_updated_at` | Trigger | Refreshes `updated_at` before every update. |

## `employees`

Stores employee profiles, store membership, authorization role, account status, and login credentials.

| Column | Data type | Constraints | Description |
| --- | --- | --- | --- |
| `id` | `BIGINT` | Primary key; generated by default as identity | Internal employee identifier. |
| `store_id` | `BIGINT` | Not null; foreign key to `stores.id`; delete restricted | Store to which the employee belongs. A store cannot be deleted while it has employee records. |
| `created_by_id` | `BIGINT` | Not null; self-referencing foreign key to `employees.id`; delete restricted | Employee who created this employee record. The initial `admin` employee references its own `id`. For all later employees, the backend derives this value from the authenticated user. |
| `username` | `VARCHAR(50)` | Not null; unique | Case-sensitive username used to sign in. For example, `admin` and `Admin` are treated as different usernames. |
| `name` | `VARCHAR(100)` | Not null | Employee's display name. |
| `gender` | `VARCHAR(10)` | Nullable; check constraint | Optional gender value. Allowed values: `MALE`, `FEMALE`, and `OTHER`. |
| `phone` | `VARCHAR(20)` | Nullable | Contact phone number, preferably normalized to E.164 format, such as `+16045550123`. It is not unique. |
| `password_hash` | `VARCHAR(255)` | Not null | BCrypt or Argon2id password hash. New accounts initially use `123456`, but only its salted hash is stored. Plain-text passwords must never be stored or returned by the API. |
| `role` | `VARCHAR(20)` | Not null; default `STAFF`; check constraint | Authorization role within the store. Allowed values: `OWNER`, `MANAGER`, and `STAFF`. |
| `status` | `VARCHAR(20)` | Not null; default `ACTIVE`; check constraint | Employee account and employment status. Allowed values: `ACTIVE` and `INACTIVE`. |
| `created_at` | `TIMESTAMPTZ` | Not null; default `CURRENT_TIMESTAMP` | Time at which the employee record was created. |
| `updated_at` | `TIMESTAMPTZ` | Not null; default `CURRENT_TIMESTAMP`; database update trigger | Time at which the employee record was last updated. |

The employee table does not store a Social Insurance Number (SIN).

### Employee gender values

| Value | Meaning |
| --- | --- |
| `MALE` | Male. |
| `FEMALE` | Female. |
| `OTHER` | Another gender value. |

### Employee role values

| Value | Meaning |
| --- | --- |
| `OWNER` | Store owner with full employee-management permissions. |
| `MANAGER` | Store manager who can manage staff members. |
| `STAFF` | Regular employee without employee-management permissions. |

### Employee status values

| Value | Meaning |
| --- | --- |
| `ACTIVE` | The employee is active and may sign in. |
| `INACTIVE` | The employee is inactive and may not sign in. |

### Employee constraints and indexes

| Name | Type | Definition |
| --- | --- | --- |
| `employees_pkey` | Primary key | `id` |
| `employees_store_fk` | Foreign key | `store_id REFERENCES stores(id) ON DELETE RESTRICT` |
| `employees_created_by_fk` | Foreign key | `created_by_id REFERENCES employees(id) ON DELETE RESTRICT` |
| `employees_username_unique` | Unique constraint | `username` (case-sensitive) |
| `employees_gender_check` | Check constraint | `gender IS NULL OR gender IN ('MALE', 'FEMALE', 'OTHER')` |
| `employees_role_check` | Check constraint | `role IN ('OWNER', 'MANAGER', 'STAFF')` |
| `employees_status_check` | Check constraint | `status IN ('ACTIVE', 'INACTIVE')` |
| `employees_set_updated_at` | Trigger | Refreshes `updated_at` before every update. |

## Relationships

```text
stores (1) --------< employees (many)
                         |
                         +---- created_by_id ----> employees.id
```

- Each employee belongs to exactly one store.
- One store can have many employees.
- Every employee has a creator recorded in `created_by_id`.
- The first `OWNER` account uses its own `id` as `created_by_id`.
- Every later employee references the authenticated employee who created the account.

## Initial store record

The first planned location is represented by the following values. The location and postcode must be updated when the exact premises are confirmed.

| Column | Initial value |
| --- | --- |
| `name` | `Coffee & Tea` |
| `status` | `PREPARING` |
| `location` | `UBC Vancouver Campus` |
| `city` | `Vancouver` |
| `province` | `BC` |
| `country` | `CA` |
| `postcode` | `V6T 1Z4` |
| `timezone` | `America/Vancouver` |
| `currency` | `CAD` |

## Initial employee record

The first employee is the store owner and system administrator. Because no earlier employee exists, this record uses its own generated `id` as `created_by_id`.

| Column | Initial value |
| --- | --- |
| `store_id` | The `id` of the initial `Coffee & Tea` store |
| `created_by_id` | The employee's own generated `id` |
| `username` | `admin` |
| `name` | `admin` |
| `gender` | `NULL` |
| `phone` | `NULL` |
| `password_hash` | A newly generated salted hash of `123456`; never the plain-text value |
| `role` | `OWNER` |
| `status` | `ACTIVE` |

The initial seed must obtain the next employee identity value before insertion and use the same value for both `id` and `created_by_id`. Hard-coding `id = 1` is not allowed because it can leave the identity sequence out of sync.

## Initial employee password policy

- Every newly created employee account receives the initial password `123456`.
- The backend hashes `123456` separately for each account before persistence, so accounts do not need to share the same stored hash.
- API requests and responses never expose `password_hash`.
- The shared initial password is acceptable only for local development. Before production deployment, it must be replaced with a one-time random password or an account activation flow that requires the employee to choose a private password.
